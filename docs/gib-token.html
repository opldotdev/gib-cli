The gib ref token

A signed pointer, never a container. A 1-sat push-drop coin whose fields name one on-chain outpoint. Its spend chain is the branch; its signature is the publisher's claim.

What it is

  • A ts-stack PushDrop coin — fields locked in the script, signed by the issuer under a BRC-100 protocol key; the publisher's key is recoverable from the token (fromIdentityKey).
  • Pointer semantics: the fields hold an outpoint — the root output of a tree (directory or directory-record). The token never embeds content; a fork can therefore name someone else's existing outpoint and copy zero bytes.
  • Origin (defined term): the genesis outpoint of the ordinal — where this token was born. A fact about the coin, one hop, no traversal.

Signing is claiming

The token names a root; the root's manifests name entries; entries chain to tips. The issuer's signature therefore covers the whole assembled tree — every file, foreign or not. Selection is authorship: you adopted exactly what you pointed at, and txid hashes make that selection unverifiable-to-change by anyone else. Claims stack: the tree publisher claims the composition; file publishers upstream claim their files; each layer verifies on its own.

Lifecycle

  • Mint = first push (or fork): a transaction creating the coin citing a root outpoint — your genesis or someone else's.
  • Move = spend forward as a new signed token citing a new root. Fast-forward = cite forward; force-push = cite an earlier root — the branch rewinds; only the abandoned data is un-deletable.
  • Rewrite = spend forward with a freshly inscribed full directory cited instead of a diff chain: prunes accumulated diffs without changing the branch's name or lineage. Available, not primary.
  • Branch vs tag is behavior, not format: a tag is a ref nobody moves.
  • Two pointers, kept straight: the coin says where the branch tip is; your checkout's HEAD (what you're building on) is local .gib state the wallet never sees. Coin ≈ git's remote branch; local ref file ≈ git's local branch; they may legitimately disagree.

Wallet integration (BRC-100 facts, verified)

  • Names are tags written once. Tags cannot be mutated in wallet storage, but a tag on a moving coin stays put while the coin moves beneath it — that's what makes a tag a usable branch name.
  • List-by-tag returns tx blobs. The wallet is an address book for outputs we published: query our refs → get the coin and the transaction that created it → the fused-shape commit rides inside, so tip sync can start with zero network fetches. Foreign records never pass through our wallet; discovering foreign history is always walk-from-outpoint.
  • No get-by-txid. The wallet is never a history store; the CLI's local cache is.
  • Sign+process is the whole motion: one wallet action funds, signs payment inputs, and broadcasts. No sign-but-hold at the wallet level; drafts/stash placement is an open question owned by the CLI doc.
  • Token payload limits: fields hold a pointer — small by design. If a payload ever exceeded field capacity, pointer-not-container is what saves us.

Updating a token with a commit (fused tx)

tx = {
  inputs:  [ <current ref coin>, funding... ],
  outputs: [
    [0] B-0 record(s):     file record + manifest cascade, each citing a lower vout
    [1] ref coin (1 sat):  fields cite the topmost manifest output in this tx
  ]
}
// record(s) are v0..; the ref at v1 cites them — nothing points forward.
// Sat-to-sat mapping is unaffected by vout position since records are 0-sat.
  • Atomicity: no window where the commit exists but the branch hasn't advanced — git's local commit-then-move-ref is one act on-chain.
  • Unpushed commits are expressed by not fusing: commit publishes records; push spends the ref separately. Fusion is the optimization, the split is the model.
  • Audit: a coin's spend chain is a signed history of every push.

Open

  • Push-drop key derivation: one key vs per-token derived keys (implying the root identity key is embedded for validators). ProtocolID/keyID unset.
  • Tagging policy: refs certainly; whether to also tag our published records while held (the wallet as a free cache) or keep tags minimal.
  • Push scope: what announcing an outpoint to an overlay/indexer is.
