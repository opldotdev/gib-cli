On-chain Git

Git semantics on BSV. Content is published once as B-0 OP_RETURN outputs; every later change is one unspendable output: a pointer to a previous on-chain root plus a standard git diff. Nothing is composed, merged, or rewritten on-chain. Any output in the graph is a complete readable state — walk back, materialize, apply diffs. Git checkout, with outpoints as commit IDs.

Agreed live between shruggr and 1sat-tester, 2026-09-17. v4 replaces the v2/v3 directory-JSON-patching model after a worked example showed directory line patches are unnecessary: git paths address files, directory entries are anchors. Groundwork verified against 1sat-stack, ORDFS, ts-stack, and the 1Sat SDK at current head.

Two things exist: outputs and coins

  • B-0 OP_RETURN outputs — all content. Genesis inscriptions, gib diff records. Unspendable, immutable, named by outpoint. Not ordinals; no wallet involvement. Except for genesis, full content is never recorded on-chain — it is a state machine only.
  • 1-sat coins — all pointers. Ref tokens (branches/tags), spendable precisely so they can move (spend forward) and be deleted (burn). See Refs.

Genesis: an ord-fs upload

Genesis is an existing ord-fs directory inscription (B-0; the 1sat-sdk already publishes these). Directory JSON maps names to outpoints or _N siblings:

// txid_4_0 — root directory of a project
{
  "index.html": "_1",
  "js":  "txid_1",   // subdirectory inscription
  "css": "txid_2",
  "favicon.ico": "txid_3"
}

Nothing about this is new; gib borrows ord-fs resolution unchanged.

The record: one base + one git diff

An update is a single B-0 output (working content type application/x-gib): a small metadata header (base outpoint; diff ref or inline) and the standard git diff text:

record := {
  base: <root outpoint>,          // e.g. txid_4
  diff: { ref: <outpoint> }       // an existing on-chain diff, or
      | { inline: <git diff text> }
}
  • Paths in the diff are ordinary repo paths relative to the base root — js/app.js. One section per file (diff --git a/… b/…), multi-file diffs native, hunks standard, index lines as the author's content guard.
  • Structure rides for free. New files (new file mode, full content inline — the genesis exception), deletions, and renames (rename from/to with zero content bytes) all come from git's format. The directory JSON is never patched; the directory state at a record is base manifest ∪ diff-added ∖ diff-deleted, computed at resolution.
  • The record's outpoint names the new tree state. Example: base txid_4, hunk to js/app.js → record at txid_5. Basing on txid_4 forks; basing on txid_5 stacks. Refs point wherever readers should enter.

Resolution: the lens

resolve(P) = apply(diff_P, resolve(base_P)) — recurse to genesis; the chain stores deltas and pointers, composed state exists only as the answer to "resolve this outpoint." Viewer-side work only; nothing composes on-chain.

  • Path lookup crosses both addressing layers: fetch base root, walk the manifest chain for the path (js → txid_1 → app.js → outpoint → bytes), materialize into a worktree, git apply the record's hunks.
  • Directory entries are anchors. A content change never flips a JSON line; the entry identifies the file's genesis, its current bytes come from the hunks above it in the chain. Renames move the anchor in the resolved view without touching inscriptions — and because git apply operates on resolved bytes, a rename carries any hunks applied earlier under the old path. Pointer-swap economics, state-correct semantics.
  • File state is addressed (outpoint, path) — versioning at the tree, like git. git log file is a derived view: walk the chain, collect sections touching the path. Files have no record chains of their own.
  • Complexity is a caching problem. Cache by (outpoint, path); transaction cache is the packfile.

Graph shape

  • One base per record, always. The graph is a tree; no fan-in nodes.
  • Branches fall out for free: two records sharing a base, both first-class.
  • Merge is composition by reference, zero new bytes. Alice and Bob publish against the same base; a third record with base: alice, diff: {ref: bob} applies Bob's hunks onto Alice's resolved state. Because hunks address resolved content, disjoint-file edits compose cleanly; same-region edits fail loudly at apply time (context mismatch) rather than silently picking a winner. When a clean composition is impossible, the author publishes an ordinary inline-diff record instead. No central management is assumed — competing merge records can coexist; consumers choose which outpoint to follow.
  • No conflicts on-chain; errors are loud. A diff that fails to apply is a bad record: resolver errors, publisher ate the fee, graph stays well-formed.
Off-chain validation rule (normative): do not publish what won't apply. Validate before inscribing; merge sanity is author-side responsibility.

Refs: signed push-drop coins (the only UTXOs)

A ref (branch head, tag, release pointer) is a 1-sat coin in the wallet — a signed push-drop token via ts-stack's PushDrop template: fields locked in the script, signed by the issuer under a BRC-100 protocol key, publisher key recoverable from the token (fromIdentityKey).

  • Move = spend forward as a new signed token; delete = burn. Names are BRC-100 tags written once (tags can't be mutated in wallet storage — verified — but a tag on a moving coin is stable while the coin moves beneath it).
  • Branch vs tag is behavior, not format: a tag is a ref nobody moves.
  • Pin vs follow: store an outpoint to pin a state; use ORDFS :-1 on the ref coin to follow the tip.
  • Signed releases (Apple-code-signing analogue): every ref update is signed; auto-update = resolve tip, verify signature against issuer identity, apply. Trust anchors on deterministic BRC-100 derivation — no PKI. Certificates above this later, if ever.
  • Private and never globally searchable: refs live in wallets; an outpoint someone hands you is the only bootstrap.

CLI & local model (gibsv)

Project: code/bsv/gibsv; local state dir .gib (cache, materialized worktrees, downloaded history — disposable, rebuildable from refs). Wallet holds only ref coins.

Verified groundwork

  • ORDFS serves raw B-0 output bytes: GET /content/<outpoint> plus :-1 tip semantics (production gateway api.1sat.app).
  • ord-fs machinery in @1sat/actions (ordfs/manifest.ts, outputs.ts); server-side resolveDirectoryPath in 1sat-stack (depth 8). Genesis publish = buildOrdFsDirOutputs — audit before leaning on it.
  • ts-stack PushDrop template: packages/sdk/src/script/templates/PushDrop.ts.
  • Live mainnet round-trip through the bitplan wallet/CLI stack: ec68da0d…1069_0.
  • Spike (2026-09-17, 13 tests vs real git 2.47) validated the record envelope, resolver walk, wrong-base loud failure, caching, and merge-by-reference. It was built on the v3 manifest-patching model; its git-integration findings survive (below), its manifest- patching design does not.
Git-integration facts that survive the redesign: git apply requires --unidiff-zero for -U0 patches or it rejects them even when lines match byte-for-byte; patches applied via a temp file in the worktree (piping via stdin hangs under execFile); materialize the target file under the name the patch declares (+++ b/<name>); a diff meeting a wrong base fails loudly via context/index mismatch — which is the validation property we rely on.

Open questions

Not yet settled
  • Push-drop key derivation (user-flagged): probably not one reused signing key per publish; per-token derived keys imply embedding the issuer's root identity key so validators can derive/verify. ProtocolID/keyID convention unset.
  • Context-adjacent edits across lenses: same-file, nearby-but-non-overlapping hunks from different authors may fail git apply's context matching though semantically compatible. Options: author with reduced context, 3-way apply against the authored-against state, or accept loud failure. Undecided.
  • Envelope serialization details (metadata header form) — draft in code.
  • Whether merged records cite the outpoints whose work they folded (provenance metadata).
  • CLI command surface (init/clone/publish/refs) unwritten.
  • Multi-batch genesis for very large trees — later optimization.

Deliberately out of scope

  • Encryption / group membership — bitplan's envelope belongs above, not inside, the record.
  • Ownership / update authority — none at this layer; fully open and public, anyone may publish a record on any base.
  • Viewer/explorer UX; indexing/discovery — above this layer.
