Draft design · v5 multi-chain model · supersedes v1–v4

On-chain Git

Git semantics on BSV, with the file chain as the spine. Every file is a chain of B-0 outputs — its genesis bytes plus diff records, each extending the previous tip, wherever that tip lives. Directories are views: inscriptions naming the current tip outpoint of each entry. A repository is one such view; editing cascades tip updates up the manifest tree to a root that a ref coin names. Any single file resolves by walking only its own chain — never by replaying a repository.

Agreed live between shruggr and 1sat-tester, 2026-09-17. v5 replaces v4's single-chain-per-repository model after a granularity review: with one base spine per repo, a file has no identity outside its repo, linking to one file means replaying the whole tree, and files maintained by other people (the package-management / publisher use case) can't be extended in place. v4's entry anchors named file genesis; v5 entries name the current tip and edits cascade. The v3 failure was making directory line-patches the content diff — v5 keeps standard file hunks as content diffs and uses manifest diffs only to move entry pointers.

Two things exist: outputs and coins

  • B-0 OP_RETURN outputs — all content. Genesis inscriptions, gib diff records. Unspendable, immutable, named by outpoint. Not ordinals; no wallet involvement. Except for genesis (and full-rewrite inscriptions), complete file content is never recorded on-chain — it is a state machine.
  • 1-sat coins — all pointers. Ref tokens (branches/tags), spendable precisely so they can move (spend forward) and be deleted (burn). A token is a signed pointer, never a container: it names an outpoint rather than holding bytes, which is what lets a fork reference existing content without copying it (see Refs).

The chain: per-file, foreign bases welcome

A file's history is a chain: its genesis output (raw bytes) extended by diff records, each record's base being the previous tip of that file. Nothing requires the base to be yours. A record can extend anyone's on-chain output — a file in your project, or a public file published by a stranger in an unrelated project. Ownership is irrelevant to the mechanism; a diff is a diff.

  • A directory is a grouping of chain tips. Directory JSON maps names to tip outpoints. Two entries in one directory may belong to entirely different projects — one chain rooted in your genesis, another continuing a stranger's publication. Resolution walks each cited chain independently.
  • The repository is a view, not a container. It carries no history of its own beyond its manifest edits. This is what git can't do: in git a file is only "path within repo at snapshot"; in gib the file's chain exists first and the directory just points at it.
  • Patchwork worktrees are normal. One checkout can contain files from many ancestries. The entry point (the root the token names) is the checkout's origin; a file's foreign chain is raw material, not ancestry.

Origin: selection is authorship

The publisher of a directory adopts everything it points at: by naming an outpoint, you own the pairing. The txid makes adoption exact and auditable — anyone can verify the directory names exactly that output, exactly those bytes. So origin is one hop, never a traversal: "the origin of everything this entry point points to" is literally the entity that pointed at them. A checkout has one entry point but many ancestries, and that is a feature — package management and publisher signatures fall out of the same mechanism, because a dependency is a pointer into another chain, exact by construction, and the signer of a chain is its publisher.

Genesis: an ord-fs upload

Genesis is an existing ord-fs directory inscription (B-0; the 1sat-sdk already publishes these). Directory JSON maps names to outpoints or _N siblings:

// txid_4_0 — root directory of a project
{
  "index.html": "_1",
  "js":  "txid_1",   // subdirectory inscription
  "css": "txid_2",
  "favicon.ico": "txid_3"
}

Nothing about this is new; gib borrows ord-fs resolution unchanged. At genesis every entry's tip is its genesis — each file output is the head of its own (one-output) chain.

The record: one base + one git diff

A change is a single B-0 output (working content type application/x-gib): a small metadata header (base outpoint; diff ref or inline) and the standard git diff text:

record := {
  base: <outpoint being extended>,   // a file tip, or a directory manifest tip
  diff: { ref: <outpoint> }          // an existing on-chain diff, or
      | { inline: <git diff text> }
}
  • The base is per-file. Editing js/app.js extends that file's current tip outpoint, wherever it lives. Different files in the same commit may extend different bases, in different projects.
  • Paths in the diff are relative to the base. One section per file (diff --git a/… b/…), hunks standard, index lines as the author's content guard (use --full-index so resolvers can verify pre-images).
  • Git's format carries structure for free: new files (new file mode, full content inline — the genesis exception), deletions, and renames (rename from/to with zero content bytes).
  • Directory manifests are files too. A manifest update is a record whose base is the previous manifest's tip and whose diff is an ordinary git diff of the JSON. One mechanism for everything.

The edit cascade

Because entries name tips, a file edit produces a new tip that must be recorded where it is referenced — upward, all the way to the root the token names:

edit js/app.js   → record R  { base: txid_9_2 }              // new file tip: txid_11_0
update js/       → record M1 { base: js-tip,  diff: manifest JSON hunk }  // "app.js": → txid_11_0
update root      → record M2 { base: root-tip, diff: manifest JSON hunk } // "js": → M1
push             → token spends forward citing M2
  • One mechanism all the way up: the manifest edits are just gib diffs against the previous manifest. No special-case "directory changed" operation.
  • All references point backwards, so the whole cascade can fuse into a single transaction: output 0 = file record, then each changed manifest above it, topmost manifest cited by the ref coin output. Nothing references a later output. (Fee/cost economics of cascades: open.)
  • The property this buys: no child-crawling, ever. Every state is fully described by walking down from its root — which is the only direction the chain can answer.

Resolution: read one file without the repo

Path lookup is a descent plus a per-file walk: fetch the root manifest (walking its diff chain to full JSON if it is one), descend through directory manifests to the entry's tip outpoint, then walk that file's chain to any full-content node and apply the hunks above it. Linking to one file touches only the chains on its path — the repository as a whole is never replayed.

  • Per-file history is native: log <file> is just that file's chain. (In git this is a derived view computed by replaying tree changes; here it is the base structure.)
  • Complexity is a caching problem. Cache by outpoint; the transaction cache is the packfile.

Graph shape

  • One base per record, always. Records form trees (per file, per manifest); no fan-in nodes.
  • Fork = a bare mint. Branching from someone else's repository is spending nothing: mint your own ref token whose pointer names their root outpoint. No bytes copied, no diff — a fork is a pointer, which is all a branch ever was. Your first edit cascades upward under your token; their token is untouched, and your token named a specific outpoint, so their later moves change nothing about yours.
  • Branches fall out for free: two records sharing a base, both first-class.
  • Merge at the view level is trivial: a new root manifest whose entries name the tips you want from each side. Reconciling two versions of the same file is one authored record whose diff applies to one side's resolved bytes. diff: {ref} keeps composition-by-reference available with zero new bytes.
  • No conflicts on-chain; errors are loud. A diff that fails to apply is a bad record: resolver errors, publisher ate the fee, graph stays well-formed.
Off-chain validation rule (normative): do not publish what won't apply. Validate before inscribing; merge sanity is author-side responsibility.

Refs: signed push-drop coins (the only UTXOs)

A ref (branch head, tag, release pointer) is a 1-sat coin in the wallet — a signed push-drop token via ts-stack's PushDrop template: fields locked in the script, signed by the issuer under a BRC-100 protocol key, publisher key recoverable from the token (fromIdentityKey). The token is a signed pointer, never a container; its identity is its spend-chain, and what it names can change underneath it.

  • Move = spend forward as a new signed token; delete = burn. Names are BRC-100 tags written once (tags can't be mutated in wallet storage — verified — but a tag on a moving coin is stable while the coin moves beneath it).
  • Two ways to move forward: cite a diff (the cascade), or inscribe a whole new directory and cite that — the branch identity survives, and the accumulated diff pile is pruned without the branch changing name or lineage (an orphan/squash move). The rewrite path is available, not the primary one.
  • Branch vs tag is behavior, not format: a tag is a ref nobody moves.
  • Pin vs follow: store an outpoint to pin a state; use ORDFS :-1 on the ref coin to follow the tip.
  • Signed releases (Apple-code-signing analogue): every ref update is signed; auto-update = resolve tip, verify signature against issuer identity, apply. Trust anchors on deterministic BRC-100 derivation — no PKI. Certificates above this later, if ever.
  • Private and never globally searchable: refs live in wallets; an outpoint someone hands you (or the wallet's own tag list) is the only bootstrap.

Commit and push are two acts

Commit publishes data. Push moves a pointer. Git fuses them locally (commit writes the object and moves the ref); gib separates them so that "committed but unpushed" and force-push are expressible.

  • Commit = wallet action(s) (sign+process: fund, sign payment inputs, broadcast) creating B-0 record outputs funded by ordinary UTXOs. A file's record set plus the manifest cascade can ride one transaction; a push can ride it too. Moving no ref is the default: a record no ref cites is gib's dangling object — real, permanent, unreachable.
  • Push = spend the ref coin forward with its fields citing some root outpoint. Forward-cite is a fast-forward; back-cite to an earlier root is a genuine force-push — the branch rewinds, and only the abandoned data is un-deletable. Announcing the outpoint onward (overlay/indexer) is further scope, still open.
  • Fusion optimization: file record(s) + manifest cascade + advanced ref coin in one transaction; every internal edge points backwards (record → base in an earlier tx; each manifest → lower vout; ref → topmost manifest). Git-style atomicity at the cost of not expressing unpushed commits.
  • Audit trail: a ref coin's spend chain is an exact, signed history of every push to that branch.
  • Bootstrap bonus: listing a tagged ref coin returns its tx blob, which in the fused shape contains the commit itself — a client syncing the tip receives the latest change with the pointer; the walk begins only when going further back.

Init, genesis-as-first-commit, and project identity

  • gib init touches nothing on-chain. Like git init it is free, reversible, local-only: create .gib, start with an unborn main — git's refs/ is literally empty until the first commit, and so is gib's.
  • The first commit is genesis, not a diff. The whole folder publishes as an ord-fs directory batch (B-0 outputs, possibly several txs — batch shape open, see below). The root directory output (<txid>_0) is the genesis commit's ID. The first push mints the branch's ref coin pointing at it.
  • Branching from an existing repo needs no genesis and no diff: resolve their root outpoint into a folder, mint a token citing it. Local setup is the same table either way.
  • origin is a defined term: the genesis outpoint of the entry point's chain — the identity of what you adopted, one hop (see Origin). Git stores no project metadata at all (not even the folder name); its root commit is the de-facto identity, and gib makes that explicit.
  • Refs mirror git's file layout: .gib/refs/heads/<name> is one line holding the tip's outpoint; HEAD names the standing branch. For committed branches the wallet coin is authoritative for the branch tip and the file is a rebuildable mirror (the coin ≈ git's remote branch; the file ≈ git's local branch; they may legitimately disagree the way main lags origin/main). HEAD — what your working tree is based on — is local only; the wallet never knows what you're working on.

CLI & local model (gibsv)

Project: code/bsv/gibsv; local state dir .gib (cache, materialized worktrees, downloaded history — disposable, rebuildable from refs). Wallet holds only ref coins.

The manifest table (.gib)

On checkout, gib persists one row per file: path → tip outpoint → content hash. All three columns earn their place: the tip outpoint is what a future diff extends (per-file, possibly a foreign chain), and the hash is how gib detects edits — worktree hash ≠ manifest hash means changed. No mtimes, no stat tricks. The table is, locally, exactly the directory manifests as walked: the neighborhood snapshot of where you're standing. Per-entry provenance is transitive — each row's chain terminates wherever it terminates.

Wallet roles (BRC-100 facts, verified)

  • No get-by-txid. The wallet cannot hand back arbitrary transaction history; gib's .gib tx cache owns downloaded history (the packfile equivalent).
  • Tagged outputs return tx blobs. Wallet list-by-tag yields ref coins with their transactions — the wallet is an address book, but only ever for outputs we published ourselves; other people's records never pass through our wallet. Discovery of foreign history is always walk-from-outpoint.
  • The action's sign+process motion IS commit. One call: fund, sign payment inputs, broadcast. There is no wallet-level sign-but-hold; whether gib wants drafts/stash (and where they'd live) is open.

Verified groundwork

  • ORDFS serves raw B-0 output bytes: GET /content/<outpoint> plus :-1 tip semantics (production gateway api.1sat.app).
  • ord-fs machinery in @1sat/actions (ordfs/manifest.ts, outputs.ts); server-side resolveDirectoryPath in 1sat-stack (depth 8). Genesis publish = buildOrdFsDirOutputs — audit before leaning on it.
  • ts-stack PushDrop template: packages/sdk/src/script/templates/PushDrop.ts.
  • Live mainnet round-trip through the bitplan wallet/CLI stack: ec68da0d…1069_0.
  • Spike (2026-09-17, 13 tests vs real git 2.47) validated the record envelope, resolver walk, wrong-base loud failure, caching, and merge-by-reference. It was built on the v3 manifest-patching model; its git-integration findings survive (below). The v4 code in code/bsv/gibsv (10/10 green) implements the single-spine model — it needs the per-file-base + cascade rework to match v5.
Git-integration facts that survive the redesign: git apply requires --unidiff-zero for -U0 patches or it rejects them even when lines match byte-for-byte; patches applied via a temp file in the worktree (piping via stdin hangs under execFile); materialize the target file under the name the patch declares (+++ b/<name>); a diff meeting a wrong base fails loudly via context/index mismatch — which is the validation property we rely on.

Open questions

Not yet settled
  • Cascade cost economics: every content edit writes a file record plus a manifest record per level above it. Single fused tx vs multiple; acceptable fee amplification for deep trees; whether manifest diffs can ever batch across independent edits.
  • Manifest tip vs genesis in diffs: when extending a foreign file, a resolver needs the chain from the cited tip; confirm whether records should ever also cite the file's genesis for fast bootstrap.
  • Push-drop key derivation (user-flagged): probably not one reused signing key per publish; per-token derived keys imply embedding the issuer's root identity key so validators can derive/verify. ProtocolID/keyID convention unset.
  • Context-adjacent edits across lenses: same-file, nearby-but-non-overlapping hunks from different authors may fail git apply's context matching though semantically compatible. Options: author with reduced context, 3-way apply against the authored-against state, or accept loud failure. Undecided.
  • Drafts/stash: the wallet has no sign-but-hold; if gib wants reviewable built transactions, decide where they live (wallet, .gib local draft, or no drafts — validate hard then one atomic call).
  • Push scope: what announcing an outpoint to an overlay/indexer actually is.
  • Output tagging policy: refs certainly; whether to tag our published records while held (wallet as free cache) or keep tags minimal.
  • Envelope serialization details (metadata header form) — draft in code.
  • Whether reconciled records cite the outpoints whose work they folded (provenance metadata).
  • CLI command surface (init/clone/publish/refs) unwritten.
  • Genesis batch shape (flagged 2026-09-17): the first commit is an ord-fs directory batch, not a single tx — unresolved complexities in how the batch is laid out (tx ordering, _N sibling references across txs, root-outpoint selection as the genesis commit's ID, tx-size/fee limits). Discussion deferred; design it before publishing real genesis.
  • Multi-batch genesis for very large trees — later optimization.

Deliberately out of scope

  • Encryption / group membership — bitplan's envelope belongs above, not inside, the record.
  • Ownership / update authority — none at this layer; fully open and public, anyone may publish a record on any base.
  • Viewer/explorer UX; indexing/discovery — above this layer.
