ordfs binary formats: ordfs/dir and ordfs/patch

Two new content types for the ord-fs family, defined here for gateway (1sat-stack/pkg/ordfs), SDK publishers, and any reader. Integers are fixed-width, big-endian unless stated; no varints; no padding. All digests are SHA-256.

Content type family

Convention going forward: new types use the non-hyphenated ordfs/ prefix. Files keep their natural MIME. No gib-namespaced types exist — gib's identity lives in its commit-token push-drop fields, not in content types.

ordfs/dir — binary directory manifest

dir :=
  [1B  version]            0x01
  [2B  entry count]        uint16
  [entries × N]            sorted ascending by raw name bytes

entry :=
  [1B  flags]
       bit0  KIND      0 = file, 1 = directory
       bit1  EXEC      executable            (file)
       bit2  SYMLINK   content = target path (file; bytes are a relative path string)
       bit3  REFTYPE   0 = same-tx output, 1 = full outpoint
       bits4–7         MUST be zero; non-zero = invalid manifest
  [1B  name length]        1..255
  [NB  name]               raw UTF-8 path COMPONENT; must not contain 0x00 or '/'
  [target]
       REFTYPE 0:  [1B vout]                     sibling output in the same tx
       REFTYPE 1:  [32B txid][4B vout]           exact Bitcoin outpoint bytes
                                                  (txid internal/LE byte order,
                                                  vout little-endian, as in a tx input)

Entry size = 3 + name + (1 or 36). A directory is 3 + Σ(entries). Example — root with LICENSE from an earlier tx and three same-tx children (sorted: LICENSE, README.md, package.json, src):

01 0004
08 07 "LICENSE"    <32B txid> <03000000>
00 09 "README.md"  01
00 0c "package.json" 06
01 03 "src"        0B

Invariants (canonical form)

  • Sorted, unique names. Same logical directory ⇒ byte-identical encoding ⇒ stable SHA-256 of the whole manifest. Readers SHOULD verify sortedness.
  • Components only. Full paths resolve by traversing multiple dirs; a name never contains '/'.
  • Default entry: same convention as JSON — an entry named ., else index.html. No dedicated field.
  • ≤256 outputs per publishing tx (one-byte same-tx vout). Writers also cap txs by cumulative bytes; large files stream.
  • Version byte: readers reject unknown versions. Any future change to the format bumps it.
  • No sharding: entry count is capped by uint16; a directory that large is out of scope.

ordfs/patch — record

patch :=
  [1B  version]            0x00
  [36B base outpoint]      native Bitcoin outpoint (internal-order txid + LE vout)
  [..  vcdiff delta]       RFC 3284 — standard header (D6 C3 C4 00) + windows
  • Base is any content — ordinal, B-protocol output, or another ordfs/patch. A chain is patches linked by base; the manifest entry names the chain tip.
  • Resolved bytes = apply(delta, resolve(base)), recursively to the root base (full bytes). The result is a new version of the base file.
  • Serving: resolved content inherits the base's declared content type (a patch output itself declares only ordfs/patch).
  • The base chain must terminate at a non-patch (or a patch whose base is unreachable is unresolvable).
  • Identical content is never a patch. Cite the existing outpoint from the manifest. An empty delta is invalid.

VCDIFF profile (on-chain contract)

The delta is RFC 3284 VCDIFF with a plain header. Writers MUST emit this profile; readers MUST reject anything else. Equivalent to xdelta3 -e -n -S none -A (and to xdelta3-wasm xd3_encode_memory with flags 0).

header := D6 C3 C4 00 00
          magic | ver | Hdr_Indicator = 0
  • Hdr_Indicator = 0: no VCD_DECOMPRESS (secondary compression), no custom code table, no application header.
  • Delta_Indicator = 0 on every window (sections uncompressed).
  • No xdelta3 Adler-32 window checksum (Win_Indicator bit 0x10 unset).
  • xdelta3 CLI default output is not this profile (djw secondary + app header). Do not write it. Interop test: encode with the flags above, decode with any RFC-plain decoder (xdelta3-wasm, @ably/vcdiff-decoder, xdelta3 -d).

Gateway behavior (1sat-stack/pkg/ordfs)

  1. Resolve outpoint → check inscription content type: ord-fs/json → existing JSON handling; ordfs/dir → binary handling; anything else → existing file/stream handling.
  2. Parse dir; on any violation (bad version, unsorted/duplicate names, reserved bits, name with 0x00 or '/') → 400 invalid directory manifest.
  3. Match the next path segment against entry names (exact byte compare). REFTYPE 0 → sibling output in the same tx (equivalent of JSON "_N"); REFTYPE 1 → that outpoint. KIND dir + remaining segments → recurse (existing maxDirectoryDepth = 8); KIND file + remaining → 404.
  4. Directory with no path → default entry (. then index.html), else the existing listing/error behavior.
  5. ordfs/patch requested directly → resolve chain, apply vcdiff, serve with the base's content type (Range/stream semantics unchanged; a streamed large file's resolved bytes are what chunk).

Publishing (1sat-sdk)

  • Directory deploys emit ordfs/dir outputs (replacing ord-fs/json writes); manifest cascade = full re-inscribe of touched dirs, one new output per directory, parents citing child outpoints.
  • gib additionally writes ordfs/patch record outputs; the SDK needs no gib-specific logic — a patch is just an output with these bytes and content type.
  • Writers MUST emit canonical form (sorted, reserved bits zero, ext count 0).
