3. Got wrong (recorded so it isn't repeated)

The big one: commit was built against the wrong model. gib commit republishes the entire tree via deployOrdfsDir. That violates the format's core rule: content is write-once; genesis is the only full publish; every later state is a record citing a base outpoint ([1B version][1B diff type][36B base][git diff]). No record output has ever been created. The diff-type registry is unexercised. Commit, and the record-resolution half of clone, are the unbuilt core of the project — everything else is scaffolding that works.
Sequencing error. Status/branch bookkeeping was built around the republish hack and needs rework at the same time as commit (manifest entries must distinguish leaves vs records).

Smaller mistakes, all now captured in the onesat-env skill: pushes signed but silently never broadcast (wallet-api doesn't run the task loop — monitor must run alongside); treated createAction's unsigned txid as a broadcast; probed protocol validity with a call that bypasses validation; published a debug file (67ff7e9b.rawtx.hex) to chain forever — no ignore-file rule existed.

4b. Corrected read-path design (agreed 2026-09-18, supersedes parts of §3)

Further superseded same day: no .gib directory at all — repos are plain git repos with gib://<origin> remotes; ONE global txstore per install; wallet is the ref database. See gib-cli.html (rewritten) for current architecture.

Cache every transaction, forever. A transaction is the immutable, self-verifiable unit: content-addressed by txid; recompute-the-txid-over-parsed-bytes proves provenance. The current read path (per-file content fetches via a hand-rolled ordfs.ts) is throwaway scraping and is being replaced.

  • txstore: local store of every tx gib has ever seen. Read path becomes ensure(txid) → parse outputs locally (B.decode) → manifests, leaves, and records all resolve from the store. Nothing is ever refetched or invalidated.
  • Transport: GET /1sat/beef/{txid} for a single tx; GET /1sat/ordfs/stream/{outpoint} streams the whole BEEF for an ord-fs tree in one request — a genesis clone is one fetch, not N. Metadata endpoints with :seq history and origin correlation handle spent-output resolution server-side.
  • NO content from ORDFS — fundamental requirement. Gib reads transactions, period (BEEF from chain/wallet → txstore). Gib correlates on-chain tx history with the on-disk working tree: diffs, checkouts at any historical point, resolved from records and manifests parsed locally. ORDFS is only a slight indexer for ordinal/origin correlation lookups. Every content/<outpoint> call is removed, not demoted — there is no fallback use. Rendering for dumb ORDFS consumers is irrelevant; gib is its own format (no browser reads git objects either).
  • Manifest cascade is definitional, not optional: a manifest is its entry list; when an entry's tip changes the manifest's bytes change → new output → parents republish up to a new root. No frozen-subdir + root-override schemes.
  • ordfs.ts is deleted outright — no replacement client needed for the data path; tx fetching is BEEF + SDK parsing. The recursive tree walk stays in gib as manifest-cascade logic over the txstore.
  • Record chains fit the store: each record cites a base outpoint; reading a file walks txids, each hop one cached tx. Tradeoff accepted: a coalesced tx with 500 files means fetching 500 files to read one — publish-time tx batching is the mitigation (design point for the commit rewrite).

5. Confidence

High: content addressing (outpoints as citations), the ORDFS read path, the token model (mint/spend/verify is proven on chain, not just in code), fee/dust correctness, clone byte-fidelity, the wallet-API patterns (now documented).
Low / untested: the record envelope has never existed outside the design doc — base-outpoint wire encoding, diff application, and manifest mixing of record/leaf pointers are design-only. Multi-directory record chains (a commit touching files in two subdirs, manifests cascading) are unthought-through. Token lineage across branch names (currently one implicit branch). Anyone-but-the-author clone: never attempted from a fresh identity/wallet.
Known unknown: how the chain handles a 36-byte binary outpoint inside an otherwise-text manifest ecosystem — decided to keep records binary and manifests JSON, but nothing on chain proves the tooling won't mangle it.
