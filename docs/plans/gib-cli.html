The gib remote

Gib does not reimplement git and has no workflow commands. It is a remote: a git-remote-gib helper git execs, plus a small setup surface for wallet and transaction store. Git is the local compute layer — disposable, authoritative over nothing. The chain is the source of truth. The wallet is gib's database.

Architecture

  • Git (local, disposable): real git does local development — staging, draft commits, status, merge machinery, conflict resolution. A gib repo contains a real git object store, rebuilt from chain state at will; wipe it and rebuild from the chain, never the reverse.
  • txstore (immutable cache): every transaction gib has ever seen, stored by txid, verified by recomputing the txid over parsed bytes. One global store per install (the single gib application owns it — no per-repo copies); portable repo bundles are an explicit export, not the store's layout. Nothing is ever refetched or invalidated.
  • Wallet = database of record for refs: one wallet per gib install; branch inventory is the wallet's basket/tags; list-by-tag returns full transactions, so "what do I have and where are my branches" is answered with zero network calls. There is no local-remote fiction.
  • Chain = everything else: all content reads are transactions (BEEF from chain/overlay sources). No content is ever read from ORDFS — ORDFS is at most a slight indexer for origin/sequence correlation.

Command semantics (final 2026-09-18: git stays git)

There are no gib workflow commands. Everything inside the repo is pure git — gib is the remote, reached through the git-remote-gib helper. Only push (write) and fetch/pull (read) touch chain state.

commandwhat happens
git add / commit / status / branch / log Local git only. Gib is never invoked. Drafts, amends, and rewrites are free and never reach chain.
git push origin main
(remote = gib://<origin>)		 The on-chain event. Helper receives the pack + ref update; per new git commit: publish record/leaf outputs + manifest cascade + commit head (fused tx, § anatomy), sealing against the current token. Ref lifecycle = coin lifecycle (mint on first push, spend forward, rewind on force-push, burn on delete).
git fetch / pull Read side: resolve the remote's tokens → commit heads → resolve objects → update local refs. Foreign history comes from the txstore/chain, never the wallet.
git clone gib://<origin> Fetch + checkout via the helper; writing (push) requires wallet coins — foreign clone can't seal against someone else's token (fork semantics TBD).

Anatomy of a gib commit transaction

PHASE 1 — content txs, ONE OR MANY (no single-tx requirement):
   record outputs:  [1B version][36B base outpoint][vcdiff delta] — one per changed
                    file; unchanged files emit NOTHING
   leaf outputs:    raw bytes — one per new file (that file's genesis)
   manifest outputs: FULL new entry list — one per touched dir, plus the new ROOT;
                    unchanged entries cite existing outpoints
   batch freely: small commits may fuse; big commits split per-file/per-dir; a single
   huge file may stream across several txs. Effective size soft limits, not consensus
   limits — reading one file must not force downloading 50 MB of unrelated changes.
   Content is PROVISIONAL until cited: unreferenced published data is orphaned
   (permanent, harmless) if the push dies before phase 2. gib keeps a pending-upload
   cache to recover/resume interrupted pushes.

PHASE 2 — commit head tx (last, always exactly one):
   inputs:  [ <previous commit token>, funding... ]   (first push: no coin — mint)
   outputs: [ COMMIT HEAD: 1-sat ordinal; pushdrop locking script
                ["gib", origin, branch name, root outpoint, identity pubkey]
              + INSCRIPTION on that same output = the git commit object
                (verbatim bytes) ]
   keyID = the new root outpoint — computable because content landed first.
  • The commit head is one output: pointer, identity, and git meaning are inseparable — spending the token carries the commit object with it. Manifest full-re-inscribe is the initial choice (one-read resolution; byte difference negligible at normal directory widths); diff-encoded manifests remain format-compatible later — a parent cites whichever output exists, and JSON vs record-envelope distinguishes them.
  • Everything git syncs is present: blobs/trees reconstruct from manifests + chains (file modes — open question), commit object verbatim (hashes recreate exactly), branch name from the field. Annotated tags: same verbatim treatment.
  • First push of a new repo (genesis): no previous coin, no records — every file publishes as a raw leaf, all manifests published, and the commit head is minted rather than spent. The genesis root directory outpoint is the origin (self-contained: origin resolves straight to the entry list). Auto-mint on first push follows ssh/file-transport precedent: pushing a new branch to a null/empty gib remote mints the repo and reports the new gib://<origin> URL; explicit create remains available as sugar.
  • Validation gate: after content txs land, before sealing — resolve the new root through gib's resolver and confirm git hashes match the sealed commit object byte-for-byte.

Local state — there is no .gib (decided 2026-09-18)

  • Gib is one application, not a per-project state directory. A gib repo is a plain git repo whose remote URL is an origin outpoint: git remote add origin gib://<origin>. Branch tracking, HEAD, identity — all native git. Multiple named gib remotes per repo are the user's business.
  • Global by design: one transaction store and one wallet per install. Token→repo association comes from origin tags written by gib at mint/publish time, not from files in the working tree.

Repository metadata: the .gib file (decided 2026-09-19)

Git has no notion of a repository name; hosts keep that in their own database. gib keeps it in the tree: a committed dotfile .gib at the root, JSON, published and cited like any other file.

{
  "name": "gib-test",
  "description": "Small repo for exercising gibhub.net",
  "defaultBranch": "main"
}
  • name, description: display metadata. Labels, not identifiers — the origin outpoint stays the repository's identity, and two repositories may claim the same name. Uniqueness and user/repo URLs are a registry concern above this layer (1sat.name for the user part).
  • defaultBranch: the branch clones should check out — git's HEAD symref, which otherwise has no chain home. The helper advertises @refs/heads/<defaultBranch> HEAD when the file resolves.
  • Readers: gibhub and the overlay fetch /content/<root>/.gib from a head's root and store name and default branch alongside the head. gib itself never needs the file. Unknown keys are ignored; a missing file means "unnamed".
  • Written by gib init; forks inherit it until edited. This is a file in the repository, not the local .gib/ state directory (which no longer exists).

gib init

gib init [-y] [--name] [--description] [--default-branch] [--remote origin] [--force] runs in the project directory. If it is not a git repository yet it runs git init -b <defaultBranch>, so a gib-first user needs one command. It prompts for name (default: directory name), description, and default branch (default: current branch), writes .gib, and adds the remote as gib://new unless a gib remote already exists. Nothing touches chain. The user commits and pushes as usual.

On the first push the helper mints the repository, then rewrites the remote URL to gib://<origin> and prints it, so the next push extends the same repository instead of minting another. Refs pushed in the same batch join the new origin.

Interface requirements (git-remote-gib)

  • Advertise: wallet list-by-tag → per branch: latest commit head → decode its inscription → sha → <sha> refs/heads/<name>. HEAD-as-symref (default branch) comes from .gib defaultBranch (see metadata).
  • Push intake: old-sha in git's ref-update must equal the sha our token names (double-check); ingest pack → objects → records + cascade + commit inscription + token spend. Ref lifecycle = coin lifecycle: create=mint, delete=burn, ff=spend forward, force=rewind cite, non-ff w/o force=reject.
  • Fetch (self): pure wallet/txstore read. Fetch (others): walk-from-outpoint over chain/overlay data — foreign data never passes through the wallet.
  • Async honesty: git's OK means durable; chain OK means broadcast vs mined. Local "pushed" = broadcast-accepted; failure surfacing later is CLI chatter, configurable.

Implementation notes (verified, supersedes all prior)

  • Codec: vcdiff (RFC 3284) only — vcdiff-wasm runs under Bun; pure-JS decoders exist. Git diff formats are out of scope by decision.
  • Live proof state: genesis dir, first commit, and a 4-coin token chain are MINED on mainnet (see gib-status.html). Token mint/spend/verify via BRC-100 wallet API works today. The record envelope, cascade-on-change, and resolver do not exist yet — no record has ever been created.
  • Current code (code/gib-cli): publish/clone/token/push work; commit is a republish hack; ordfs.ts scraping still present and must be removed per no-ORDFS-content rule; directory policy stays local, mechanics go upstream to the SDK; pushdrop mint/move lifecycle goes upstream (lifted from OPNS).
  • Git commit object measured 126 B minimal / 200–300 B typical — rides the pushdrop tx easily.

Open

Unsettled
  • File modes: git tree entries carry exec bit/symlink marks; manifests don't. Add modes to manifest entries, or store tree objects verbatim.
  • Cascade fee economics and tx batching; coalescing tradeoff (big tx vs per-file fetch).
  • Annotated-tag tx shape (own fused tx vs riding a commit).
  • Clone-from-stranger flow: mint own token citing foreign root; new repo ID on fork — first-edit mechanics.
  • Publish-skip policy (.gitignore-style rules for the genesis batch).
