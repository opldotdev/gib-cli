Why gib is shaped this way

Design record: the tensions that forced each choice, and the dead ends that were walked and backtracked. Normative specs live in the sibling docs; nothing here is required to implement.

Repository-first lost to file-first

Mimicking git's whole-tree model (v4: one base spine per repository, record = one multi-file diff) borrows all of git's machinery cheaply — and inherits its ceiling. In git a file is only "path within repo at snapshot"; a file's identity and history exist only inside a repository. On-chain, the point is a graph where files point to files across projects maintained by different people — package management and publisher signatures from the same substrate. A repository-first chain forces the whole tree to resolve and replay to link one file, and gives files maintained elsewhere no place to live. The per-file edit work attempted on top of v4 failed not because per-file was wrong but because the diffs it produced still had a repository-shaped home.

v5 makes the file chain the spine and demotes the repository to a view: a directory inscription naming tips. Directories cost nothing extra to version, because a manifest is a file and manifest updates are ordinary gib diffs — the cascade is one mechanism, not a second system. The cost paid: every edit writes several outputs (open economics question), and no dedupe (below).

Content-addressing at envelope granularity

Outpoints are content-addressed — the txid hashes the whole transaction: payload, inputs, change, signatures. Immutability is inherited by containment, pointers still can't lie. Two prices, same root cause: identical bytes published twice are two outputs (git dedupes by construction; gib can only dedupe by choosing to cite an existing output — provenance, not prevention), and an output's ID isn't knowable before funding decisions, though it is knowable before broadcast once signed. Git's "here's my commit hash before I push" becomes "publish-then-cite" — which the fused commit+push transaction absorbs.

Why content hashes are stored anyway

Git's diff format already carries them (index abc..def pre/post images) — full --full-index hashes let resolvers verify pre-images before applying, independent of the transaction. The local manifest table adds a hash per file for a different job: cheap change detection at the worktree. Neither is a lookup service — a hash in hand proves membership only in a set you already hold; "is this content already published?" needs an indexer, which is deliberately out of scope.

All references point backwards

On-chain, newer cites older, full stop: a transaction knows nothing of future children. "What's on top of this output?" is unanswerable without having seen everything — git is the same (object parents only; GitHub's fork list is a crawler). The cascade turns that limitation into a design rule: tips are recorded upward, so every readable state descends from a root a token names, and no client ever crawls children. Reverse indexes, when they exist, belong to indexers above the layer.

Commit and push are separable

Git fuses them locally; fusing on-chain (one tx: record + ref advance) buys atomicity but can't express "committed, unpushed" or force-push. The model keeps them separate — commit publishes data and moves nothing (dangling records are real, permanent, unreachable); push moves the pointer, forward or backward. Fusion survives as an optimization because every edge inside the fused tx points backwards.

Token as pointer, not container

For a normal commit the models converge — the fused tx carries the content beside the coin, and the coin cites it one output over. They diverge at fork time: a container-token copying someone's directory re-inscribes immutable public bytes and mints a duplicate outpoint for identical content; a pointer-token forks by naming the existing outpoint, zero bytes. The case that decides it is the one git models best — a branch is a hash in a file — so the token copies that: identity via spend-chain, content via citation. The container move stays available where it means something: a rewrite re-inscribes a fresh directory and recites the pointer, pruning a long diff pile under an unchanged branch identity.

Dead ends, recorded

  • v2/v3 — patching directory JSON as the change model. Diffs of manifest line-patches became the repository's history; a worked example showed git paths already address files, so directory patches were redundant machinery. (Manifest diffs survive only as tip updates — the cascade — never as content diffs.)
  • Overnight per-file attempt on v4. File-level diffs bolted onto a single-spine repo graph; correct instinct, wrong substrate.
  • "Content is the pointer." Overreach: refs are not inscriptions; refs are coins. Content addresses content; tokens address tips.
  • Tag-everything. Tagging every published output as a wallet cache fails: foreign outputs never pass through our wallet. Tags cover what we publish; the rest is walk-from-outpoint.
  • Merge-by-reference (diff: {ref}: apply someone else's stored diff instead of writing your own). Made sense for repo-shaped changesets; in file chains, chains are linear and conflicts need an authored reconciliation anyway. Dropping it freed the diff field to become a typed codec registry (git / vcdiff / append), which composition-forbidding codecs like VCDIFF require.

Accepted tensions

  • Snapshot cost: git's show is instant (snapshots); gib's resolve is a chain walk. Caching mitigates; the delta-only chain is the point.
  • Fees scale with graph depth (cascade) where git's cost is flat per commit.
  • No modes/symlinks: directory JSON has nowhere for executable bits or symlink flags — an implicit v1 data-format loss.
  • Trust at genesis: genesis outputs carry no self-declared hash; resolvers trust the fetch source unless they verify against a cited manifest hash chain.

Deliberately out of scope

  • Encryption/group membership — bitplan's envelope sits above the record, not inside it.
  • Ownership/update authority — this layer is fully open: anyone may extend any base.
  • Indexing, discovery, explorer UX — above this layer; the wallet is the only directory service below it.
