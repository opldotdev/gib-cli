The gib command line tool

Project code/bsv/gibsv. The CLI is where the bulk of development lives: checkout state, the manifest table, the cascade, wallet calls, and the git-shaped commands over all of it. The on-chain format stays minimal so the CLI can stay smart.

Local state — the .gib directory

  • Disposable and rebuildable from the wallet's tokens plus the chain, like .git.
  • The manifest table — one row per file: path → tip outpoint → content hash. Persisted at checkout. The tip outpoint is what a future diff extends (per file, possibly a foreign chain); the hash is change detection: worktree hash ≠ table hash means edited. No mtimes, no stat heuristics.
  • The table is locally what the walked manifests are on-chain — a snapshot of the graph neighborhood the checkout stands in. Per-entry provenance is transitive: each row's chain terminates wherever it does.
  • Refs mirror git byte-for-byte: .gib/refs/heads/<name> is one line with the tip outpoint; HEAD names the standing branch. Committed branches: the coin is authoritative, the file a rebuildable mirror (rebuilt via wallet list-by-tag). Unborn branches live only here — git's refs/ is empty until first commit, and so is gib's.
  • The transaction cache is the packfile: the wallet has no get-by-txid, so downloaded record/genesis transactions live here.

Core flow

checkout: token (wallet) → root outpoint → walk manifests down → materialize files
          → write manifest table (path, tip, hash) → set HEAD
edit:     normal file edits; status = worktree hash vs table hash
commit:   per changed file: author git diff against its tip (full-index), validate applies,
          publish record; then cascade manifest records up to root; optional fusion with push
push:     spend ref coin forward citing new root (or fused into the commit tx)
  • New files need naming: a diff isn't enough — the parent manifest gains an entry, so the cascade is mandatory whenever a file is added, deleted, or renamed at the directory level.
  • Different files, different bases: commit determines the base per file from the table, so one commit's records may extend chains rooted in several projects.
  • Validate hard, then one atomic call: the wallet has no sign-but-hold; the review gate is the CLI's pre-publish apply check. Whether gib grows drafts/stash (and where they live) is open.

Implementation notes (verified)

git plumbing facts: git apply needs --unidiff-zero for -U0 patches even when lines match; apply via temp file in the worktree (stdin piping hangs under execFile); materialize targets under the name the patch declares (+++ b/<name>); wrong base fails loudly via context/index mismatch — the validation property the whole system leans on.
  • ORDFS gateway serves raw B-0 bytes and :-1 tip follow (api.1sat.app); ord-fs publish via @1sat/actions buildOrdFsDirOutputs — audit before trusting with a real genesis.
  • Live mainnet round-trip: ec68da0d…1069_0.
  • Current code state: 10/10 tests green, but built on v4's single-spine model. The per-file-base + cascade rework is the next build phase.
